photo-gen

Validated target: MacBook Air M5, 16 GB unified memory, 8-core GPU, macOS 27.0 (26A428).

Performance figures and profile validation here are specific to this machine and environment. photo-gen is not currently a general-purpose, cross-platform package; other hardware may work but has not been validated (docs/HARDWARE.md).

A local image generator for one machine: a command-line tool and a localhost HTTP API that run Z-Image-Turbo through mflux on Apple's MLX framework. It's built and validated for a MacBook Air M5 with 16 GB of unified memory. Since 2026-10-07 it also has an experimental image-editing task (Qwen-Image-2.1, research licence, non-commercial) that shares the same queue, job store and API (Image editing).

First image in 60 seconds #

No background needed. Run these from the project root (<project-root>, the directory containing bin/). The FAST profile at 1024×1024 took 54 s on a cool machine (measured), and longer once the fanless Air has heated up.

1. Check the installation

bin/photo-gen verify

It prints JSON ending in "ok": true. If it doesn't, see Model integrity failure.

2. Generate

bin/photo-gen generate -p "a red apple on a wooden table, soft window light" --profile fast --seed 42

3. Find the output

The command prints the image path, then the seed, time, pixel hash and metadata path:

<project-root>/data/outputs/YYYY/MM/DD/<job_id>.png
  seed=42  time=…s  pixel_sha256=7b45cfbe…
  metadata=<project-root>/data/outputs/YYYY/MM/DD/<job_id>.json

Reproducibility check

With exactly this prompt and seed, the FAST profile at 1024² produces pixel hash 7b45cfbe… (full: 7b45cfbe2eed1cd1…). Getting the same hash means your installation reproduces the validated result bit for bit.

Open the image with open data/outputs/…/<job_id>.png, or use the HTTP API (Quick start).

What is photo-gen? #

photo-gen is a local text-to-image application. It wraps one research-validated inference backend, Z-Image-Turbo run by mflux on MLX/Metal, in an application layer that provides:

  • a CLI (bin/photo-gen) and a localhost HTTP API (stdlib http.server, port 8765);
  • a persistent SQLite job store, with a queue that runs one generation at a time across the whole machine;
  • a fresh worker process per image, with memory behaviour matched to a 16 GB machine;
  • startup verification of runtime versions and model file hashes, refusing to run on drift;
  • a JSON metadata record per image, with a canonical pixel hash and a reproduce command.

The problem it solves. It runs a modern 6B-parameter image model on a fanless 16 GB laptop, reproducibly, without memory-pressure failures, and without a GUI or cloud service. Scripts and local agents can drive it over HTTP.

Application vs. research project

The application

app/, bin/, config/, data/. This is what you run. It changes only when research has produced evidence for a change.

The research project around it

research/. The evidence trail: benchmarks, blinded quality gates, audits and negative results. Every production behaviour has a report behind it. photo-gen is also used as an inference research platform (see Research mode).

Quick start #

Start the API server

bin/photo-gen serve

It runs the startup checks, then logs photo-gen API listening on http://127.0.0.1:8765. Stop it with Ctrl-C or SIGTERM; both shut down gracefully. Use serve --full-verify to re-hash every model file first.

Generate from the CLI

# FAST profile (bf16 + 8 steps), validated at 512², 768² and 1024²
bin/photo-gen generate -p "a lighthouse at dawn" --profile fast --seed 42

# REFERENCE profile (fp32 + 9 steps). Also what you get with no profile/precision flags.
bin/photo-gen generate -p "a lighthouse at dawn" --profile reference --seed 42

# ULTRA profile (bf16 + 4 steps): 512×512 ONLY
bin/photo-gen generate -p "a lighthouse at dawn" --profile ultra --width 512 --height 512 --seed 42
bin/photo-gen generate -p "a lighthouse at dawn" --seed 42

# Other validated sizes for REFERENCE
bin/photo-gen generate -p "a lighthouse at dawn" --width 512 --height 512 --seed 42

# Full machine-readable job record
bin/photo-gen generate -p "a lighthouse at dawn" --profile fast --seed random --json

The CLI runs the job in its own process. If the API server is generating at that moment, the CLI waits for the machine-wide GPU lock.

Call the HTTP API

curl -s -X POST http://127.0.0.1:8765/generate \
     -H 'Content-Type: application/json' \
     -d '{"prompt":"a lighthouse at dawn","profile":"fast","seed":42}'

The response is 202 with the job record. Note its job_id.

Wait for / retrieve the job

# long-poll: returns as soon as the job is completed/failed/cancelled, or after 300 s
curl -s "http://127.0.0.1:8765/jobs/<job_id>?wait=300"

# download the PNG
curl -s -o image.png http://127.0.0.1:8765/outputs/<job_id>

HTTP API reference #

Implemented in app/photogen/api.py. JSON in and out. It binds to 127.0.0.1:8765 by default.

Local-only protections

Requests whose Host header isn't 127.0.0.1, localhost or ::1 get 403. For POST requests, a non-local Origin gets 403, and a body that isn't Content-Type: application/json gets 415. Bodies are limited to 64 KB. There is no authentication; the loopback bind is the security boundary. Changing server.host exposes the API to your network, and a warning is logged.

REFERENCE: fp32 + 9 steps

This is the permanent, intentionally conservative reproducibility baseline. In mflux every step is one transformer evaluation, so 9 steps = 9 NFE (network function evaluations). That is one more than the official Turbo recipe. REFERENCE is not "the official Turbo configuration"; it is deliberately kept unchanged so every result stays comparable. Regression pixel hashes (prompt "a red apple on a wooden table, soft window light", seed 42): 1024² fe47d88d…, 512² 9ae59f59…, 768² 94a023d3… (the 768² hash was first recorded 2026-09-25 in the Phase 3 cold runs).

FAST: bf16 + 8 steps

8 steps = 8 NFE, the official Z-Image-Turbo evaluation count as currently understood. The model card's "9 steps → 8 DiT forwards" was an artifact of an old diffusers version (research/experiments/scheduler-nfe-note.md). Regression hash at 1024², same prompt, seed 42: 7b45cfbe….

What "validated" means for FAST, exactly

On 2026-09-25, FAST was compared directly with REFERENCE in three pre-registered blinded gates, 24 pairs each (12 prompts × 2 fresh seeds). Results: 512²: 0 REFERENCE-better / 0 FAST-better / 24 ties; 768²: 2 / 0 / 22; 1024²: 0 / 1 / 23. All five non-ties were object-level differences (e.g. a duplicated object), split between the arms. Earlier, 1024² had been supported only by a chain of two gates (fp32/9→bf16/9→bf16/8). Limits: a single AI rater, 24 pairs per size. Details: research/experiments/fast-resolution-gates-report.md.

How the build enforces this

  • --profile fast at 512², 768² or 1024² runs as validated.
  • --profile fast at any other size is refused unless you pass --allow-experimental; it then runs with a warning and validated_configuration: false.
  • --profile ultra (bf16 + 4) is validated at 512² only: blind vs FAST 1 / 0 / 23 at 0.51× denoise (cold wall 15.6 → 9.5 s). At 768² and 1024² it is refused without --allow-experimental, because 4-step Turbo showed specific text/object-resolution failures at 768² and 1024² under the fresh-seed blinded gate (ghosted duplicate text, malformed letters, ghost objects; research/experiments/step-count-quality-gate/results.md).
  • --profile balanced (bf16 + 5) is validated at 1024² only: blind vs FAST 0 / 0 / 24, paired denoise 0.63× FAST (cold wall 54.4 → 36.1 s; hash befe1b3c…). At 768² the Stage B gate passed by the narrowest possible margin (3 / 0 / 21, every non-tie favouring 8 steps), a focused, pre-registered 32-pair confirmation was then not confirmed (3 / 1 / 28; the small poster subtitle failed in both seeds), so 768² stays on FAST and BALANCED is refused there without --allow-experimental. At 512² it is not offered: ULTRA is validated there and faster.
  • 7/6 steps, 5 steps at 512²/768², and 4 steps above 512² need --allow-experimental. The original step sweep's "5–4 = preview" label came from a small, unblinded seed-42 assessment and was superseded by blinded evidence (annotated in step-sweep-report.md).

Validity is per exact combination

The build validates the exact combination of precision + steps + resolution against one explicit table (VALIDATED_COMBINATIONS in app/photogen/runtimes/mflux_zimage.py): fp32 + 9 and bf16 + 8 at 512², 768², 1024²; bf16 + 9 at 1024² only (the only size where it was gated); bf16 + 5 (BALANCED) at 1024² only; bf16 + 4 (ULTRA) at 512² only. Anything else needs --allow-experimental and is recorded as validated_configuration: false. A configuration never becomes valid because a nearby one was gated. (Before 2026-09-28, bf16 + 9 at 512²/768² was mislabelled as validated; corrected, with a regression test.)

Precision: fp32 and bf16 #

"Precision" here means the data type of the diffusion transformer's activations (its hidden stream). The weights are always the same q4 file, and nothing on disk changes.

fp32 REFERENCE

This is unmodified mflux 0.20.0 behaviour. mflux loads the model as bf16, but two float32 inputs (the timestep embedding and the RoPE tables) promote the whole hidden stream to float32 (research/experiments/E02-RESULTS.md, confirmed by ablation E10). fp32 is the default.

bf16 ADOPTED AS OPT-IN

The worker applies in-process casts so the hidden stream stays bfloat16: timestep-embedding output, RoPE result, SDPA mask, and pad tokens (a no-op, kept for byte-identical parity with the gated experiment). No mflux file, weight, quantization or scheduler changes (_apply_bf16_stream in app/photogen/runtimes/mflux_zimage_worker.py).

  • Output: deterministic, but not pixel-identical to fp32. The same seed gives a closely similar image with small content differences.
  • Quality evidence: passed a blinded gate on 24 pairs at 1024², 9 steps: 0 fp32-better / 2 bf16-better / 22 ties, no text regression. The limitations are a single rater, 24 pairs and one resolution. The gate rules out a meaningful regression at that sample size; it does not show "identical quality".
  • Speed: bf16/9 vs fp32/9 denoise ratio 0.70 at 1024², both cold (55.1 vs 78.3 s) and as the median of 24 paired sustained runs.
  • Memory: lower peak footprint, 5.84 vs 6.56 GB at 1024².

Image editing (Qwen-Image-2.1) G2 REJECTED RESEARCH OPT-IN #

Not a production feature · non-commercial licence

The real-photograph quality gate G2 rejected editing at both budgets (512 and 1024). On real photographs, small text elsewhere in the picture (street signs, posters, decals) is often re-drawn as gibberish, and edits leak onto similar or attached objects. Editing stays available only as a research opt-in: every edit is labelled validated_configuration: false and needs --allow-experimental. Editing uses Qwen-Image-2.1, whose weights are under the Qwen Research License (non-commercial: research or evaluation only); photo-gen's MIT licence grants no rights to them. The weights are never committed or redistributed (docs/THIRD-PARTY-LICENSES.md §5).

Phase 6 diagnostic: higher precision does not fix it

A pre-registered, arm-blind test re-ran G2's six text failures with 8-bit instead of 4-bit weights, changing nothing else. The 8-bit weights rescued 1 of 19 garbled text elements, and text still failed on 6 of 6 results. They cost about 40% more time and about 3 GB more memory at 1024. 4-bit quantization is not supported as the primary cause (research/qwen/QWEN-QQ-DIAGNOSTIC.md). Editing stays research-only.

An edit takes one input image and a natural-language instruction and returns the edited image. Typical instructions: "Change the background to a sunset beach", "Give the panda a blue scarf.", "Remove the coffee mug. Keep everything else unchanged.", "Replace the text "BAKERY" with "COFFEE", keeping the same font of the original text."

bin/photo-gen edit --image path/to/input.png -p "Change the background to a sunset beach" \
    --output-resolution 512 --seed 42 --allow-experimental

How the application labels it

  • /capabilities and /status: tasks["image-edit"].status is "research-only", and tasks["image-edit"].quality_status lists integration: validated; capability: validated (G0 CAPABLE); quality: G2 REJECTED at 512 and 1024; local production: REJECTED; availability: research/testing opt-in only; licence: Qwen Research License, non-commercial. photo-gen status prints the same on its image-edit: line.
  • Every edit job carries the warning "image-edit (Qwen-Image-2.1) is RESEARCH-ONLY: REJECTED by the real-photograph quality gate G2 at 512 and 1024 …" (the CLI prints it to stderr), and a request without allow_experimental is refused with an error that names G2. Every edit stays validated: false.

How it fits

  • Model-selective, explicit routing. text-to-image goes to Z-Image and image-edit goes to Qwen (app/photogen/tasks.py). There is no automatic model selection.
  • One job system. Edits use the same queue, SQLite store, machine-wide GPU lock, output layout, cancellation and GET /jobs/{id} as generations. A generation and an edit never run at the same time.
  • A separate runtime environment. The edit backend needs mflux 0.21.0, which also changes Z-Image's numerics, so it runs from its own venv mflux-qwen/.venv (same MLX 0.32.2). Production Z-Image stays on mflux 0.20.0 in mflux/.venv, and its pixel hashes are unchanged.
  • Isolated health. If the edit backend is missing or fails verification, only editing is disabled (503). Generation, serve and /health's service status are unaffected.

Inputs

The input is validated and staged at submission:

  • PNG, JPEG or WebP; not animated; ≤ 50 MB; each side 64–8192 px. A camera JPEG in multi-picture (MPO) form, as many Panasonic and Sony cameras write, is accepted as its primary image; the extra preview images are ignored, with a warning.
  • EXIF orientation is applied. A fully opaque alpha channel is dropped; inputs with transparent pixels are rejected.
  • An embedded ICC profile is ignored (pixel values are taken as sRGB), with a warning.
  • The result is written as a metadata-free RGB PNG at data/inputs/<pixel_sha256>.png.

The job records both the original file's sha256 and the staged pixel sha256 (request.input_image), and the staged file is re-verified before the worker starts. Over HTTP, image must be an absolute local path; the API remains loopback-only.

Outputs and reproducibility

The output PNG is RGBA (as written by mflux), next to a photogen.edit/1 sidecar that records:

  • the input identity, instruction, seed, steps, output resolution, scheduler, guidance and KV-cache setting;
  • the model, revision, licence and export identity, and the runtime versions;
  • phase and step timings, and memory;
  • pixel_sha256 (RGB, the project-wide identity) plus output_alpha (alpha range and an RGBA hash);
  • a reproduce.cli command.

Architecture #

The CLI and the API share one service layer (service.py) and one job layer (jobs.py). Inference always happens in a separate, short-lived worker process.

Tasks (since 2026-10-07). JobManager routes each job by its task through an explicit table (tasks.TaskRouter): text-to-image → MFluxZImageRuntime (the diagram below), image-edit → MFluxQwenImageEditRuntime, whose worker runs in the separate mflux-qwen/.venv. Each runtime owns its request type, its normalize() and its metadata sidecar. Everything else (queue, store, GPU lock, cancellation, output layout) is shared. The text-to-image sidecar and stored requests are pinned to their pre-Phase-4 form by a golden test.

Request lifecycle

  1. Normalize. MFluxZImageRuntime.normalize() is the single validation point. It rejects unsupported or unknown fields, resolves the profile, applies defaults, picks a random seed if asked, and decides validated and warnings. The result is a frozen GenerationRequest: exactly what will run.
  2. Persist. A row is inserted in SQLite with status queued. API jobs go onto an in-memory queue served by one background thread; CLI jobs execute immediately in the CLI process.
  3. Serialize. The executor takes an exclusive flock on data/gpu.lock, so the API server and any CLI process never generate at the same time. A waiting job can still be cancelled.
  4. Run. The status becomes running (an atomic compare-and-set). The runtime writes worker-request.json and launches the worker in a new session. It waits up to 30 minutes, and cancellation kills the process group (SIGTERM, then SIGKILL after 10 s).
  5. Validate. The image is decoded; its size must match and it must not be uniform/blank. The pixel SHA-256 and file SHA-256 are computed.
  6. Record. A metadata sidecar (photogen.generation/1) is written next to the PNG, including a reproduce.cli command and system telemetry before/after. The job becomes completed, or failed with a structured error.
Crash recovery

When the API server starts, jobs left running by a process that no longer exists are marked failed ("owning process exited"). Queued API jobs from a previous session are re-queued, unless another live server owns them.

Why generation is serialized

One generation peaks at 5.4–6.6 GB of footprint on a 16 GB machine that also runs macOS and other apps. Concurrency has never been validated here, and two concurrent generations would compete for the same GPU and memory. The lock makes "one active generation" a machine-wide guarantee rather than a per-process one.

What --low-ram does here

--low-ram is always passed and cannot be disabled; low_ram: false is rejected. In mflux it frees the text encoder before denoising, caps the MLX cache at 1 GB, and tiles the VAE decode. photo-gen adds a fix so that mflux's transformer release actually takes effect before VAE decode (next section).

Why a worker process #

A separate process per image is an engineering decision, not an accident. It's what makes the measured memory profile reproducible on a 16 GB machine.

  • Measured problem. Without --low-ram, this Mac reached a 12.8 GB footprint, critical memory pressure and 2 GB of swap. --low-ram deletes the text encoder during each run, which can't coexist with keeping a model resident in a long-lived server process. Every reference implementation surveyed keeps models resident (research/COMPONENT-SOURCES.md).
  • Lifecycle cleanup. When the worker exits, all of its memory returns to the OS. The server itself stays around 0.1 GB between jobs.
  • Isolation. A Metal/MLX crash, or an out-of-memory kill, fails one job and leaves the service running. Cancellation is a process-group kill.
  • Cost. About 2.6 s of worker start-up per job (≈3% at 1024²): interpreter start, model load ≈1.1 s, text encode ≈0.65 s.

The transformer-release fix ADOPTED

mflux's --low-ram sets model.transformer = None after the denoise loop. But mflux's compiled predict closure still referenced the ≈3.47 GB q4 transformer, keeping it alive through VAE decode. The worker rebuilds predict with an identical body that reads the transformer from a holder, and clears the holder after the loop.

The result is pixel-identical output, with no runtime cost. Peak footprint at 1024² dropped from ≈7.3 GB to 6.56 GB (fp32) and 5.84 GB (bf16). This has been reported upstream as mflux-community/mflux #760 (research/experiments/production-memory-fix-report.md).

Hash cache. A full hash of the 5.5 GB pack takes a few seconds when the files are in the OS cache, and up to ≈20 s cold. data/integrity-cache.json stores each file's inode, size and mtime after a successful full hash. A later check trusts the cache only if all three are unchanged; otherwise the file is re-hashed. --full ignores the cache.

Output identity

  • pixel_sha256 is the canonical image identity: SHA-256 of the decoded 8-bit RGB bytes. PNG bytes can differ between identical generations because mflux embeds run metadata (e.g. timing), so file_sha256 is recorded too but isn't used for identity.
  • Determinism (verified): the same prompt, seed, size, steps and precision reproduce the same pixel hash. The regression hashes on this page have been reproduced repeatedly through the CLI, the production worker and the research harnesses.
  • Blank-output guard: an image whose per-channel standard deviation is below 2.0 is rejected as output_corrupted. Research on another runtime saw all-white images returned with exit code 0.

Current limitations #

Known limitations of the current build

  • Text-to-image is Z-Image only. Editing is a separate, experimental task (Qwen-Image-2.1, research licence): a single input image, no masks or multi-reference, and no validated configuration yet. No img2img, LoRA, ControlNet or negative prompts; each is rejected explicitly.
  • Edits are slow at 1024 (≈ 8 min cold per edit) and use up to ≈ 12 GB, so close large apps first. 512 edits take ≈ 1.5–2 min.
  • One generation at a time, machine-wide. Concurrency is not validated on this hardware.
  • No progress streaming and no GUI. Use ?wait= long-polling, and step_seconds after completion.
  • ≈2.6 s worker start-up per job, the cost of the per-job process.
  • Thermal variability: 1024² REFERENCE ranges from ≈83 s cold to ≈134 s heat-soaked.
  • FAST is validated at 512², 768² and 1024² only; other sizes require allow_experimental.
  • Lower step counts (7–4) are experimental and not quality-equivalent.
  • No authentication on the API; loopback-only by design.
  • Starting a second server on a port already in use fails with a raw Python traceback (OSError: [Errno 48] Address already in use), not a friendly message.
  • CLI cancel cancels only queued jobs; a running API job must be cancelled through the API.
  • Maximum size is 1024×1024 pixels total; 2048² is not supported on 16 GB.
  • Validated only on this exact machine and environment.

Not limitations of the build: future research

Model reduction, other quantization formats, kernel work and few-step models are research topics (see What's next?), not missing features.

capabilities() → Capabilitiesdeclare what the runtime really supports: tasks, validated resolutions, seed/negative-prompt/guidance/editing/LoRA flags, output formats, precisions, profiles, text encoders, memory profile
health(full_verify=False) → RuntimeHealthnamed checks {name: {"ok", "detail"}}. Any failure blocks serve and generate.
normalize(params, defaults) → GenerationRequestthe single validation point: reject unsupported parameters, apply defaults, return exactly what will run
generate(job_id, request, output_path, work_dir, cancel) → GenerationResultproduce the PNG at output_path, honour the CancelToken promptly, report timings, memory and effective parameters

There are no separate load, cancel or unload methods. Loading happens inside generate (in the worker), and cancellation arrives through the CancelToken (token.on_cancel(callback)).

Adding another runtime: what it involves today

  1. Implement ImageRuntime in app/photogen/runtimes/<name>.py, ideally with its own worker process for the same isolation.
  2. Give it a manifest (pinned versions and model digests) so health() can refuse drift.
  3. Wiring: PhotoGenService currently constructs MFluxZImageRuntime directly, and config.py loads one manifest path. There is no runtime-selection setting yet; choosing between runtimes would need a small change in service.py/config.py.
  4. Test it with a fake like app/tests/helpers.py, then produce research evidence (parity/benchmarks) before calling it validated.

Research mode #

photo-gen doubles as a controlled inference-research platform. The application only changes when research produces evidence.

  • Reference configuration: REFERENCE (fp32/9) is permanent, so every experiment compares against the same pixels.
  • Evidence standard: exact changes need pixel parity; numeric changes need a blinded quality gate (research/experiments/blind_stage.py: prepare → freeze → unblind, with hashed keys and scores; rules in BLIND-PROTOCOL.md). Speed claims name their baseline (cold vs sustained, fp32 vs bf16) and are never multiplied.
  • Method: sequential runs only (no GPU sharing), a 1 Hz system monitor, ABBA ordering for paired timing, 600 s idle before cold runs, fresh seeds for blinded reviews.
  • Negative results are kept: rejected and closed experiments remain in the register with their evidence.
  • Provenance: sourcing decisions in research/COMPONENT-SOURCES.md; model pins in research/model-pins.txt.

What's next? #

Research directions, not currently supported production features.

  • Resolution validation: done (FAST validated at all three sizes). The sigma-schedule audit is also complete: mflux's resolution-dependent shift differs from the official static schedule but showed no quality or runtime cost (research/experiments/sigma-schedule-audit.md).
  • Model reduction: a block-sensitivity map, and a structurally valid FFN-width reduction experiment.
  • Quantization: a speed map of the other MLX formats (q3/q5/q6, group sizes, mxfp4/nvfp4/mxfp8) before any quality work.
  • Apple/MLX/Metal kernels and NAX: profiling the denoise loop, and establishing which kernels actually use the M5's neural accelerators.
  • Few-step distillation: a feasibility study only; no training planned.
